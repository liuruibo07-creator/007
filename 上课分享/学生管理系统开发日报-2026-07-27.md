## 一、今日工作概述

今日主要完成了学生管理系统从项目架构搭建到核心功能落地的全过程。项目采用控制台 C/S 架构，客户端通过 TCP Socket 与服务器建立连接，使用 Java 对象流传输统一的 `Request` 和 `Response` 对象；服务器通过多线程处理不同客户端请求，并通过 JDBC 和 Druid 数据库连接池访问 MySQL。

当前已经完成客户端、通信模型、服务端、多线程请求处理、数据库访问和 DAO 测试等主要模块，学生信息的添加、删除、修改、查询全部和按学号查询功能均已接入完整调用链。

### 4. 完成请求与响应通信模型

在 `common` 包中完成：

- `OperationType`：定义 `ADD`、`DELETE`、`UPDATE`、`SELECT_BY_ID`、`SELECT_ALL` 和 `EXIT` 操作。
- `Request`：封装操作类型、学生对象或学生学号。
- `Response`：封装操作是否成功、提示信息、单个学生或学生集合。

`Request` 和 `Response` 均支持对象序列化，使客户端和服务器可以通过 `ObjectInputStream`、`ObjectOutputStream` 传输结构化数据。

### 5. 完成 TCP 多线程服务器

编写了 `StudentServer`，使用 `ServerSocket` 监听 10010 端口。

服务器运行流程：

1. 主线程持续调用 `accept()` 等待客户端连接。
2. 每接收一个客户端连接，创建一个 `ClientHandleRunnable`。
3. 使用独立线程处理该客户端的请求。
4. 根据 `OperationType` 分发增删改查业务。
5. 将业务处理结果封装成 `Response` 返回客户端。

这种实现可以让多个客户端同时连接，某个客户端退出时不会影响服务器继续接收其他连接。

## 四、技术难点与解决方式

### 1. 客户端和服务端对象流初始化

如果客户端和服务器同时先创建 `ObjectInputStream`，可能互相等待对象流头信息，造成阻塞。

目前两端均先创建 `ObjectOutputStream`，再创建 `ObjectInputStream`，避免对象流初始化死锁。

### 2. 一个协议支持多种业务

不同操作需要携带不同数据：

- 添加、修改需要携带 `Student`。
- 删除、按学号查询需要携带学号。
- 查询全部和退出不需要业务参数。

通过 `OperationType` 配合多个 `Request` 构造方法解决了请求参数差异问题。

### 3. 多客户端并发处理

服务器主线程只负责接收连接，每个客户端交给独立的 `ClientHandleRunnable` 线程处理，防止单个客户端长时间操作阻塞其他客户端。

### 4. 数据库连接管理

使用 Druid 连接池统一管理数据库连接。DAO 每次完成数据库操作后，通过 `JdbcUtils.release()` 释放资源，将连接归还连接池，降低连接泄漏风险。

## 六、当前存在的问题

1. `StudentDAOTest` 当前主要通过打印结果判断是否成功，缺少 `assertEquals`、`assertNotNull` 等自动断言。
2. 修改学生测试中没有为测试对象设置数据库 ID，可能无法准确验证 `WHERE id = ?` 的更新逻辑。
3. 客户端对输入格式的校验较少，输入非数字菜单或非法日期时可能抛出异常。
4. 添加学生时若学号重复，DAO 异常最终会被包装成服务端异常，提示信息还不够友好。
5. 服务端端口和数据库参数目前为固定配置，后续可以进一步集中管理。
6. 客户端退出时发送了 `EXIT` 请求，但没有读取服务器返回的“已断开连接”响应就直接关闭 Socket。
7. 压缩包中包含 `.git`、`.idea`、`out` 和数据库本地配置，正式提交或分享时应注意清理编译产物并隐藏数据库密码。
