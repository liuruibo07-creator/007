## 二 在线招聘平台架构与服务治理

### 8 [P0] 为什么招聘平台采用微服务？以当前团队和业务规模，单体应用能否满足需求？

- 追问：微服务带来了哪些实际成本？为什么足球俱乐部系统使用另一种架构？

**参考回答：** 用户、职位、投递、通知、聊天有不同职责和负载特征，微服务便于独立演进、部署及故障隔离，也适合实践服务治理。但当前若团队较小、流量不高，模块化单体通常更容易开发和运维。微服务新增远程失败、跨服务事务、部署及排障成本。足球系统业务边界更集中，使用单体可以降低这些成本。

**追问要点：** 承认架构与规模有关；若采用微服务主要出于学习或课程要求，应如实说清。

### 9 [P0] 用户、职位、投递、通知和聊天服务分别负责什么？你如何确定服务边界？

- 追问：服务是否共用数据库或表？一个服务是否直接操作其他服务的表？如何处理跨服务查询？

**参考回答：** 用户服务管理账号、身份和简历；职位服务管理职位及企业发布信息；投递服务管理投递记录与状态；通知服务生成站内通知；聊天服务管理会话与消息。划分依据是业务职责、数据归属和变更频率。原则上数据由所属服务写入，其他服务通过接口或事件获取，跨服务列表可用聚合接口或读取模型。

**追问要点：** 同一个 MySQL 实例可以承载多个服务库，但直接跨服务改表会破坏边界。项目是否共库、是否存在跨表直查需按实际说明。

### 10 [P0] 请画出招聘平台的实际部署和调用关系，标明 Nacos、Gateway、Redis、RabbitMQ、数据库的位置。

- 追问：哪些组件由团队实际部署？各组件使用什么版本，版本如何选择和匹配？

**参考回答：** 逻辑链路可画为“Vue 客户端 → Gateway → 业务服务 → 各服务数据”，Nacos 负责注册与配置，Redis 提供缓存，RabbitMQ 连接投递和通知，Seata 协调选定的数据库分支。Elasticsearch 与聊天链路要按实际接入情况补上。

**追问要点：** 这只是逻辑图，不代表每个组件独立机器部署。版本从 pom.xml、锁文件、镜像标签或部署脚本读取，Spring Boot、Spring Cloud、Alibaba 组件采用兼容的 BOM，不能猜版本。

### 11 [P0] 一个服务启动后，如何注册到 Nacos，并被 OpenFeign 调用方发现？

- 追问：实例下线后调用方如何感知？你配置了哪些健康检查或实例选择机制？

**参考回答：** 服务启动时按配置向 Nacos 注册服务名、地址、端口等信息，并维持实例健康状态。调用方通过服务发现取得可用实例，再由实际配置的负载均衡组件选择实例发起 HTTP 请求。实例下线后注册中心更新状态，客户端通过订阅或刷新感知，传播期间仍可能出现请求失败。

**追问要点：** 临时与持久实例、健康机制随版本和配置不同。应展示实际客户端依赖、服务名和健康相关配置，不把“注册成功”等同于接口可用。

### 12 [P0] Nacos 配置中心和注册中心在项目中分别承担什么职责？

- 追问：如何区分开发、测试环境？配置更新后哪些值会刷新，如何验证？配置中如何处理密钥？

**参考回答：** 注册中心解决“服务在哪里”，配置中心解决“运行配置是什么”。环境隔离可通过 namespace 配合 group、Data ID 和环境文件实现，具体规则要统一。配置更新不代表所有对象自动重建，只有被实际刷新机制覆盖的配置才会生效，需用一个可观察的配置值验证。

**追问要点：** 密钥不直接提交 Git；使用受控的密钥服务或部署注入，限制配置读取权限，日志脱敏。不要把普通配置中心等同于专用密钥保险箱。

### 13 [P0] Gateway 的动态路由在项目中如何实现？请解释一条实际路由配置。

- 追问：断言、路径重写和过滤器各做什么？路由配置错误时如何定位？

**参考回答：** 路由由 ID、目标 URI、断言和过滤器构成。例如 `/api/jobs/**` 命中路径断言，按实际后端路径决定是否去掉 `/api` 前缀，转发到 `lb://job-service`。动态路由还需把配置变化转换为路由定义刷新，不是接入 Nacos 就自然具备。

**追问要点：** 排查时核对外部 URL、命中路由、重写后的路径、服务注册名和实例地址。认证过滤器处理身份，路由过滤器处理转发，两者职责不同。

### 14 [P0] OpenFeign 的超时如何设置？哪些调用可以重试，哪些调用重试可能产生重复写入？

- 追问：远程调用失败时，上游如何返回错误？如何避免一个慢服务拖住整条链路？

**参考回答：** 连接超时限制建连等待，读取超时限制等待响应；具体配置位置取决于 Feign 和 HTTP 客户端版本。查询可以在总时限内有限重试，写操作必须先有幂等依据。超时只能说明没有及时取得响应，不能证明对方没有执行。上游需区分依赖不可用和业务拒绝，配合隔离、熔断或限流避免级联阻塞。

**追问要点：** 不笼统声称 Feign 默认会重试；展示实际 Retryer、超时和客户端配置。

### 15 [P1] 如果用户服务正常，但投递服务调用用户服务一直失败，你会按什么顺序排查？

- 追问：如何区分服务发现、网络、路由、序列化和业务异常问题？如何关联多个服务的日志？

**参考回答：** 先确认失败范围和最近改动，再从投递服务所在环境检查解析和连通性；查看 Nacos 的服务名、namespace、group 与健康实例；直接请求目标接口核对路径、端口和协议；随后查 Feign 编解码、参数、超时和下游业务日志。用 traceId 串起请求链，跨线程及跨服务时显式传播上下文。

**追问要点：** 本机能请求不代表服务运行环境能请求；日志记录关键耗时与错误类型，避免输出 Token 和完整简历。

### 16 [P2] 如果职位服务短时间不可用，投递、搜索和聊天业务分别应如何降级？

- 考察点：不同业务的可用性要求，以及超时、隔离、限流和用户提示的取舍。

**参考回答：** 职位详情可在允许范围内返回缓存并提示可能延迟；投递属于写操作，如果无法可靠确认职位是否开放，不能无条件放行，可明确失败或受控受理为待确认状态；搜索可返回已有索引结果，但投递时仍以权威数据校验；聊天若有独立认证与数据链路，可继续运行，不必被职位服务故障一起拖垮。

## 三 招聘平台缓存方案

### 17 [P0] 职位信息缓存的 Key、Value 和过期时间分别如何设计？请举一个实际例子。

- 追问：缓存的是职位详情、列表还是查询结果？为什么选择这些数据？如何评估收益？

**参考回答：** 一种合理设计是缓存详情：`job:detail:v1:{jobId}`，Value 保存职位展示 DTO，TTL 按允许陈旧时间设置并加入随机扰动。列表条件组合多、更新频繁，是否缓存取决于命中率和失效成本，不能照搬详情策略。个性化投递状态不应混进全局职位缓存。

**追问要点：** Key、字段和 TTL 数值需换成实际配置；通过命中率、数据库读取下降和响应延迟证明收益。

### 18 [P0] 简历中提到空值缓存、互斥锁和随机过期时间，它们分别解决什么具体问题？

- 追问：请用请求过程区分缓存穿透、击穿和雪崩，而不是只背定义。

**参考回答：** 穿透是请求不存在的数据，缓存和数据库都查不到，空值短缓存可减少反复回源；击穿是某个热点 Key 失效，大量请求同时回源，互斥重建可收敛并发；雪崩是大量 Key 同时失效或整个缓存不可用，随机 TTL 只能缓解前者，后者还需限流、隔离和数据库保护。

**追问要点：** 三种措施各有范围，不能说加了随机时间就能解决 Redis 宕机。

### 19 [P0] 不存在的职位会缓存多久？职位新建后，旧的空值缓存如何处理？

- 追问：如果不断请求随机职位 ID，空值缓存会不会消耗大量内存？还可以怎样处理？

**参考回答：** 空值应有比正常数据更短的 TTL，例如几十秒到数分钟作为设计示例，具体由不存在请求比例和新建可见性要求决定。新建职位成功后主动删除对应空值缓存，但仍需考虑并发读写留下旧空值的窗口。随机 ID 攻击可通过参数校验、限流、容量约束，必要时结合布隆过滤器降低压力。

**追问要点：** 布隆过滤器存在误判，也有新数据维护成本；它不是鉴权机制，更不能取代数据库事实。

### 20 [P0] 缓存重建互斥锁如何加锁、释放锁？未拿到锁的请求会做什么？

- 追问：拿到锁后是否再次检查缓存？线程异常或执行超过锁有效期时会发生什么？

**参考回答：** 使用单条 `SET lockKey token NX PX ttl` 同时完成互斥和租期设置；拿到锁后再查缓存，避免重复重建。未拿到锁的请求做有限次数退避重查，超过时限返回可控错误或走受限回源。持有者查询数据库、写入缓存，并在 finally 中原子校验 token 后释放。

**追问要点：** 查询超过租期会出现重叠持有者；续期只能减少风险，不能证明旧持有者永远停止执行。涉及写入新旧版本时还需版本校验等机制。参见 [Redis 锁说明](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

### 21 [P0] 为什么不能无条件删除 Redis 锁？你如何保证只释放当前请求持有的锁？

- 追问：校验持有者与删除之间如何避免竞态？锁过期后旧持有者继续写数据怎么办？

**参考回答：** A 的锁过期后 B 可能拿到同名锁，A 无条件 DEL 会删除 B 的锁。应使用每次请求独有的 token，并通过 Lua 把“值相等才删除”合成原子操作。先 GET 再 DEL 之间仍可能发生锁过期和重新获取。

**追问要点：** 释放安全不能防止旧持有者继续写；可用版本号或由目标系统强制校验的 fencing token 拒绝旧写入。单实例租期锁不能作为强一致业务正确性的唯一依据。

### 22 [P0] 职位编辑、下架和删除时，缓存与数据库如何保持一致？

- 追问：先更新数据库再删除缓存仍然可能出现什么并发问题？你项目实际采用了什么策略？

**参考回答：** 常见 Cache Aside 做法是先更新数据库并提交，再删除缓存。这样不需要在事务提交前把尚未确定的数据写入缓存，但仍可能发生旧读回填、删除失败。可用删除重试、变更事件和版本校验降低不一致；延迟双删也只是缓解，不能保证所有调度下正确。

**追问要点：** 下架职位时，即使展示缓存短暂陈旧，投递入口也必须检查权威状态。项目已实现的策略与可改进方案分开说。

### 23 [P0] “Redis 异常时降级查询数据库”具体如何编码？哪些异常触发降级？

- 追问：如果所有流量同时回源，数据库能承受吗？如何控制并发、超时和重试？

**参考回答：** 对连接失败、命令超时等基础设施异常做窄范围捕获，记录指标，不能把序列化错误或业务异常都当成缓存故障吞掉。降级数据库查询前设置并发预算、连接和查询时限；容量不足时限流或返回繁忙，不让每个请求无约束回源。缓存持续故障时短路访问，探测恢复后再逐步恢复。

**追问要点：** 降级目的是保护核心服务，不是保证任何流量下都成功；避免每层重复重试放大请求。

### 24 [P1] 随机过期时间的范围如何确定？为什么它无法单独解决热点职位的缓存击穿？



**参考回答：** 在业务允许的有效期周围加入有界随机扰动，范围需要兼顾陈旧容忍度和失效分散程度，不能无限延长。随机化把多个 Key 的失效时间打散，但一个热点 Key 仍只有一个到期时刻，失效瞬间仍会并发回源，需要互斥重建或受控的异步刷新。

### 25 [P1] 如何确认缓存真的有效？你会观察命中率、延迟、内存和哪些业务指标？

- 追问：数据库数据与缓存不一致时，你怎样发现和修复？

**参考回答：** 同时观察命中率、空值命中率、缓存响应延迟、回源 QPS、重建等待和失败次数、内存及淘汰数量，结合接口 P95/P99 和数据库负载判断。命中率高但数据经常过期不可用，仍不能算有效。抽样比对版本或更新时间，结合业务反馈发现不一致，再按权威数据库失效重建。

## 四 简历投递与 Seata 分布式事务

### 26 [P0] 请完整描述一次简历投递，从用户认证、职位校验、防重复到通知触发。

- 追问：哪一步是本地事务，哪一步是远程调用？事务提交前后分别发生什么？

**参考回答：** 从可信身份取得用户 ID，校验请求格式、简历归属及职位是否允许投递；由数据库唯一约束拦截重复，写投递记录，再协调职位计数更新。若使用 Seata，把两个数据库分支纳入同一全局事务。成功事件必须与业务最终提交状态衔接，通知消费者幂等处理。前端对重复投递给出稳定提示。

**追问要点：** 客户端传来的 userId 不能作为身份依据；“职位开放”若要求与并发下架严格互斥，必须在职位服务端用事务内状态检查或条件更新落实。

### 27 [P0] 防重复投递的唯一索引由哪些列组成？为什么不能只靠“先查询、再插入”？

- 追问：两个相同请求同时到达时谁成功？唯一约束异常如何转换成前端可理解的响应？

**参考回答：** 若规则是每人每个职位仅保留一条投递，建立 `UNIQUE(candidate_id, job_id)`，两列均为 NOT NULL。先查再插在并发下可能都查不到，只有唯一约束能在数据库写入时仲裁；一个事务成功后，另一个会等待并最终因冲突失败，或在前者回滚后继续成功。把该特定约束的重复异常映射成“已投递”。

**追问要点：** 不要把所有完整性异常都解释成重复投递，也不要把唯一约束异常暴露成 500。若事务已标记回滚，应在事务边界之外转换为稳定响应。

### 28 [P0] 如果业务允许撤回后重新投递，唯一索引和历史记录应如何设计？

- 追问：是新增一条记录还是恢复旧记录？如何定义一次有效投递？

**参考回答：** 可以让 `(candidate_id, job_id)` 对应一个当前投递聚合，撤回后更新状态，重新投递时增加 attempt/version，另用历史表记录每次变化。并发状态变更通过版本或条件更新仲裁。如果必须每次新增，则把“唯一的当前有效投递”与历史分离，在独立当前表上保持唯一性。

**追问要点：** 不能简单把 `deleted` 加到唯一索引就宣称支持无限次历史；MySQL 可空列与唯一性语义也需明确。先确定统计的是累计次数还是当前有效人数。

### 29 [P0] 为什么要同时维护投递记录和职位投递数？投递数能否通过查询或异步汇总得到？

- 考察点：是否理解冗余计数的收益、维护成本和一致性要求。

**参考回答：** 冗余计数可减少高频展示时的聚合查询，但增加一致性、热点写入和修复成本。若规模小且索引合理，可以直接 COUNT；允许短暂延迟时可用事件汇总并定期对账。是否强一致取决于计数用途：展示热度一般可最终一致，若影响名额限制则应使用更严格的业务约束。

### 30 [P0] 项目实际使用 Seata 的哪种事务模式？为什么选择它？

- 追问：请结合所用模式解释 TM、RM、TC 的职责，以及事务发起、分支注册和结束过程。

**参考回答：** 先确认实际模式，不能仅凭“用了 Seata”就回答 AT。若确实是 AT，可说它通过数据源代理记录前后镜像，一阶段在本地事务中提交业务数据与 undo_log，二阶段成功时清理，失败时补偿回滚。TM 发起和结束全局事务，RM 管理分支资源，TC 协调全局和分支状态。

**追问要点：** AT 对 SQL、数据库和参与写入方式有约束，不等于任意资源的强隔离事务。参见 [Seata AT 官方机制](https://seata.apache.org/docs/dev/mode/at-mode/)。

### 31 [P0] 全局事务从哪个方法开始？事务标识如何跨 OpenFeign 调用传播？

- 追问：如何确认两个服务确实加入了同一个全局事务？你看过哪些日志或记录？

**参考回答：** 通常在投递编排服务的公共入口开启全局事务，下游数据库操作分别构成分支。XID 通过与版本匹配的调用集成在请求中传播，下游恢复到事务上下文；不能只加注解就假定跨服务传播已经正确。验证时关联入口、Feign 出站、下游入站和 TC 中的同一 XID，并观察分支注册与回滚结果。

**追问要点：** 方法名、注解位置、依赖集成和实际请求头应从代码确认；线程切换也可能丢失上下文。

### 32 [P0] 如果使用 AT 模式，undo_log、数据源代理和全局锁分别起什么作用？

- 追问：回滚时发生脏数据校验失败怎么办？如果实际不是 AT 模式，请解释对应机制。

**参考回答：** AT 的数据源代理拦截受支持的 SQL，采集修改前后镜像并记录 undo_log，与业务修改同一本地事务提交；提交前需要取得对应全局锁。全局锁约束参与该协调机制的写入，不能自动阻止所有绕过它的写操作。回滚时先校验当前数据与后镜像，再根据前镜像补偿。

**追问要点：** 脏数据校验失败要告警、保留事务与数据证据，按冲突来源进行人工或受控补偿，不能盲删 undo_log 或强制覆盖。参见 [Seata AT 回滚流程](https://seata.apache.org/docs/dev/mode/at-mode/)。

### 33 [P0] 投递记录写入成功，但职位计数更新失败，系统如何回滚？

- 追问：如果远程接口返回超时，但职位计数实际上已经更新，最终结果如何确定？

**参考回答：** 计数分支失败应向上抛出可触发全局回滚的异常，不能包装成成功。TC 协调已注册分支回滚；如果分支暂时不可达，事务可能进入重试而非立刻完全恢复。超时并不等于计数没改，必须根据全局事务最终状态判断，不能在调用方随意再补一笔减法。

**追问要点：** 需要事务状态监控、重试告警和对账，避免回滚重试期间对用户作出错误承诺。

### 34 [P0] 同一职位并发投递时，计数更新语句如何写，才能避免更新丢失？

- 追问：热点职位的单行计数会不会成为锁竞争瓶颈？如何验证？

**参考回答：** 使用数据库原子更新，例如 `UPDATE job SET application_count = application_count + 1 WHERE id = ?`，并检查影响行数；若要求职位开放，再加状态条件。不先把值查到 Java 再计算覆盖。撤回减计数时也要约束状态和非负条件。

**追问要点：** 原子更新避免丢失更新，不会消除热点行锁竞争。压力增大可改异步汇总、分片计数或读时聚合，但要重新定义一致性并做压测。

### 35 [P0] 全局事务回滚时，RabbitMQ 通知消息是否可能已经发出？如何防止通知不存在的投递？

- 考察点：数据库事务与消息发送之间的边界，不能默认 Seata 自动覆盖消息系统。

**参考回答：** 可能。消息如果在全局事务尚未最终提交时发出，即使后面数据库回滚，消费者也可能已经创建通知。Seata 不会自动撤回普通 RabbitMQ 消息。需要在业务最终提交后可靠产生事件，或者让事件处于待确认状态，只有核实全局最终成功后才允许发布。

**追问要点：** AT 一阶段本地提交不等于全局提交，普通本地 afterCommit 回调或被分支提前暴露的 outbox 记录不能单独解决这个问题。也可重构为投递与 outbox 在同一本地事务、计数最终一致的方案。

### 36 [P1] 你如何测试分布式事务，而不是只验证正常请求？

- 追问：分别在远程服务抛异常、调用超时、进程中断时注入故障，预期数据状态是什么？

**参考回答：** 构造正常投递、重复投递、远程业务异常、响应丢失、超时及服务重启用例。每次记录请求 ID、XID、两边数据库初末状态和通知情况，等待事务达到最终状态再判定。回滚测试要求投递与计数都恢复，通知不得对回滚投递产生有效结果；未终结事务应进入告警而不是视为成功。

**追问要点：** 故障注入应控制影响范围；测试证据包括数据断言与日志，不只是看 HTTP 返回码。

### 37 [P2] 如果不使用 Seata，你会如何设计这条投递链路的一致性方案？

- 追问：本地消息表、补偿与定期对账如何取舍？投递记录和计数是否必须强一致？

**参考回答：** 可以把投递记录和 outbox 事件放在投递库同一本地事务中提交，独立发布器把事件发到 RabbitMQ，职位服务按事件 ID 幂等更新计数，通知服务独立生成通知；发布失败重试，消费失败补偿，定期用投递事实对账计数。这提供可恢复的最终一致性，避免同步跨服务事务，但计数会有延迟。

**追问要点：** 若必须严格同步限制名额，不能直接照搬异步计数，应另设计名额预留和确认协议。

## 五 RabbitMQ 通知与消息可靠性

### 38 [P0] 投递后产生什么消息？消息体有哪些字段，为什么不直接把完整简历放入消息？

- 追问：交换机、队列、路由键如何命名和绑定？多个消费者之间如何分工？

**参考回答：** 投递成功事件可包含 `eventId`、`applicationId`、`candidateId`、`jobId`、接收方标识、发生时间与事件版本，只传通知所需的最小数据，避免复制整份简历。示例可用 topic 交换机 `application.events`，路由键 `application.submitted`，通知队列 `notification.application`。

**追问要点：** 上述为设计示例，需换成实际配置。同一通知队列的多个消费者分摊任务；不同业务需要各自队列，不能靠同一队列把每条消息广播给所有业务。

### 39 [P0] 请画出投递主流程与通知消费流程，说明引入 RabbitMQ 后接口返回时机的变化。

- 追问：通知延迟时前端如何展示？什么情况下用户能看到投递成功但暂时没有通知？

**参考回答：** 同步流程要等投递、计数及通知全部结束；解耦后投递只等待核心业务达到约定成功条件，并保证事件可恢复，再返回投递结果。通知消费者稍后生成站内信。前端立即展示投递成功，通知按实际状态显示，不能将“请求已发出”说成“通知已送达”。

**追问要点：** 异步减少接口等待，不会自动减少总工作量；通知延迟和失败需要观测及补偿。

### 40 [P0] 如何分别处理消息没有到达 Broker、没有路由到队列、消费者处理失败这三类问题？

- 追问：项目是否配置生产者确认、不可路由消息返回、持久化和手动确认？请说明实际配置。

**参考回答：** 生产者确认用于获知 Broker 是否接管消息，未确认的发送要保留可重试状态；不可路由消息需要返回机制，例如 mandatory 配合 return；消费失败使用手动 ACK、有限重试和最终失败队列。交换机、队列持久化与消息持久化还要正确配合，故障容忍要求高时选择合适的复制队列。

**追问要点：** confirm 不表示消费者完成，也不必然表示路由到目标队列。持久化不是“任何故障都不丢”的承诺。参见 [RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)。

### 41 [P0] 消费者应在什么时机 ACK？数据库写入成功，但 ACK 前进程退出会发生什么？

- 追问：通知如何做到重复消费不产生重复业务结果？幂等依据是什么？

**参考回答：** 通知的数据库事务成功提交后再 ACK。若提交后 ACK 前退出，消息可能再次投递，所以数据库应以 eventId 或“事件与接收方”的组合设置唯一约束，重复时识别已完成并确认。消费失败要回滚业务写入，再按策略重试。

**追问要点：** 目标是至少一次投递下业务效果幂等，不宣称端到端天然恰好一次。ACK 使用接收该消息的 channel，避免误确认其他消息。参见 [RabbitMQ 可靠性指南](https://www.rabbitmq.com/docs/reliability)。

### 42 [P0] 简历中的“消息重试”和“异常消息队列”具体如何实现？

- 追问：最大次数、间隔、最终去向和人工补偿入口在哪里？如何避免失败消息无限重入队？

**参考回答：** 可按短暂异常与永久错误分流：网络抖动使用有上限的退避重试；参数无效等进入最终失败处理。重试次数与业务事件 ID 可持久记录，超过阈值转失败队列并告警，修复后受控重放。重试可以由监听容器或重试队列实现，具体要按项目配置说明。

**追问要点：** 立即反复 NACK requeue 会形成热循环；死信队列也需可靠性配置和监控，不能等同于绝对不丢。重新发布重试消息时，也要处理发布失败与原消息 ACK 的顺序。

### 43 [P0] 数据库投递成功，但生产者发消息失败怎么办？消息先发送成功，事务随后回滚又怎么办？

- 追问：请描述你已实现的保障措施，再讨论可以补充的方案。

**参考回答：** 本地数据库业务可采用事务 outbox：业务记录和事件同事务写入，提交后发布，收到可靠确认后标记发送完成；中途崩溃可能重发，由消费者幂等兜底。不能先发送再写库，也不能只用“提交后发送一次”的内存回调覆盖进程崩溃窗口。

**追问要点：** 若仍保留 Seata AT，必须按第 35 题解决全局提交可见性；本地 outbox 模式不能未经设计就嵌入全局事务并声称完成一致性。

### 44 [P1] 消息积压时，你如何区分生产过快、消费过慢、下游故障与反复重试？

- 追问：如何设置预取数量、消费者并发和限流？增加消费者一定能提高吞吐量吗？

**参考回答：** 先看消息生产速率、投递和确认速率、ready/unacked 数量、消费耗时及重投比例，再查下游数据库或外部接口。处理慢则优化业务、批处理或索引；生产瞬增则限流和扩容；反复失败则隔离毒消息。prefetch 限制每个消费者未确认消息数量，并发需匹配 CPU、连接池与下游容量。

**追问要点：** 盲目增加消费者可能把数据库压垮；要观察积压消退速度与业务错误率。

### 45 [P1] 你说熟悉五种队列模型，具体指哪几种？各适合什么业务？

- 追问：通知场景为何选当前模型？如果一条投递事件同时供通知与统计使用，应如何绑定队列？

**参考回答：** 常见教学中的五种是简单队列、工作队列、发布订阅、路由和主题模式，并不是 RabbitMQ 只有五种能力。简单队列对应基础点对点；工作队列多消费者竞争处理；fanout 广播到绑定队列；direct 按路由键匹配；topic 按模式匹配。通知与统计都要收到同一事件时，应分别建队列并绑定事件路由。

**追问要点：** 消息进入多个队列后，各队列独立消费和重试；RPC 等也属于常见使用方式。

### 46 [P2] 如果同一份投递先后发生提交、撤回和重新提交，乱序消息会造成什么问题？如何处理？



**参考回答：** 为投递聚合增加递增版本或 attemptId，事件携带版本；消费者只接受符合状态转换及版本条件的更新，旧事件忽略，重复事件幂等。若业务不能跳过中间事件，则需要按投递 ID 分区串行、检测版本缺口并补拉状态。

**追问要点：** 多消费者、重试和重新入队都会影响处理顺序；不能只因同一队列通常按序投递就保证最终业务有序。

## 六 足球俱乐部系统业务深挖

### 47 [P0] 财务收支表如何设计？金额、收支方向、业务日期、所属球队和操作人分别用什么字段？

- 追问：如何表示退款、冲正和删除？为什么选择这种模型？

**参考回答：** 示例表包含主键、club_id、收支方向、正数金额、业务日期、分类、备注、创建和更新人、时间及版本号。金额可用 `DECIMAL(18,2)`，范围和小数位按业务确定；方向使用枚举约束，金额不同时承担正负与方向两套语义。俱乐部隔离必须进入查询与写入条件。

**追问要点：** 正式财务流水通常需要冲正及审计，不能随意物理删除；实践项目如果只是普通收支 CRUD，应明确它不等于完整会计系统。退款如何记账需先统一口径。

### 48 [P0] 请写出财务分页查询接口的参数、响应结构和核心 SQL。

- 追问：如何组合日期、类型、关键词筛选？如何保证排序稳定并限制分页大小？

**参考回答：** 示例参数是 page、size、type、startDate、endDate、keyword；响应为 records、total、page、size。后端校验日期范围与分页上限，身份决定 club_id，查询始终带球队范围。动态条件使用参数绑定，排序如 `business_date DESC, id DESC`，避免日期相同导致翻页不稳定。

**SQL 思路：** `WHERE club_id = ? AND deleted = 0`，按需追加类型、日期、关键词；日期使用左闭右开区间。列表与 COUNT 共用同一筛选规则，深分页再考虑游标方式。

### 49 [P0] 请手写条件聚合 SQL，一次计算总收入、总支出和净收支。

- 追问：无数据时返回什么？软删除记录是否参与计算？统计条件如何与列表筛选保持一致？

**参考回答：** 在同一条 SQL 中用 `SUM(CASE WHEN type = 'INCOME' THEN amount ELSE 0 END)` 计算收入，支出同理，再相减得到净收支，外层用 COALESCE 处理空集合。条件必须包含球队、业务日期和有效记录；若页面按类型筛选，先明确卡片是随筛选变化还是始终显示全部收支。

**追问要点：** 第 124 题有完整 SQL 示例；聚合在数据库完成可避免把所有明细拉到 Java，但仍需索引和口径验证。

### 50 [P0] 为什么金额使用 BigDecimal？从入参到计算、数据库存储再到前端展示，如何控制精度？

- 追问：如何构造 BigDecimal、比较数值和设置舍入规则？数据库字段如何选择？

**参考回答：** 二进制浮点不能精确表达许多十进制小数，金额采用 BigDecimal 计算、MySQL DECIMAL 存储。优先 `new BigDecimal("0.1")` 等十进制字符串构造，避免 `new BigDecimal(0.1)` 引入浮点近似；按业务明确 scale 和 RoundingMode。数值比较用 compareTo，equals 还比较 scale。

**追问要点：** 前端只负责显示，不能用 JavaScript 浮点合计作为权威金额。高精度金额跨 JSON 可传十进制字符串，后端重新校验和计算；舍入规则需由业务约定而非随意选择。

### 51 [P0] 财务列表和汇总卡片在并发更新时，是否可能展示不同口径的数据？业务上如何处理？

- 追问：两者是否必须处于同一快照？你如何定义可接受的一致性？

**参考回答：** 两个接口在不同时间执行，可能分别读到修改前后的数据，出现列表与卡片暂时不一致。普通管理页可以接受短暂差异并在写入后统一刷新；若要求严格同口径，可用同一后端接口在同一个适当隔离级别的只读事务中执行一致性读取。分页列表只显示部分记录，不能拿当前页小计冒充全量合计。

**追问要点：** 同一事务不自动等于同一快照，需结合数据库隔离级别及读类型；一个接口内还应复用筛选条件。

### 52 [P0] 财务记录的查看、新增、修改、删除权限分别在哪里校验？

- 追问：隐藏按钮后直接请求接口是否还能操作？如何防止修改其他球队的记录？

**参考回答：** 前端菜单和按钮控制改善交互，后端在接口或服务层检查操作权限，SQL 再加入数据归属范围。例如删除时依据认证用户可管理的球队执行 `DELETE/UPDATE ... WHERE id = ? AND club_id = ?` 并检查影响行数。不能只相信请求传来的球队 ID 或隐藏按钮。

**追问要点：** 还需防止批量接口、导出接口、详情接口绕过限制；读取与修改同样要做数据权限。

### 53 [P0] 财务记录被两名工作人员同时修改时，如何避免覆盖？是否需要审计日志？

- 追问：金额修改如何追溯？为什么可能需要乐观锁或版本号？

**参考回答：** 可增加 version，修改时带上旧版本，以 `WHERE id = ? AND version = ?` 条件更新并递增版本；影响行数为零时提示数据已变化，请刷新。审计记录操作者、操作时间、对象、变更前后值和请求标识，敏感字段脱敏。重要财务变动优先冲正而非覆盖历史。

**追问要点：** 乐观锁避免覆盖，不会自动提供完整审计；审计写入与业务变更是否同事务要按可靠性要求设计。

### 54 [P0] 请描述球队队徽上传 OSS 的完整流程，说明文件经过哪些系统。

- 追问：采用后端转传还是前端直传？凭证存放在哪里？如何限制可访问的对象范围？

**参考回答：** 若后端转传，前端用 multipart 上传，后端鉴权并校验文件，再生成对象 Key 调用 OSS，成功后更新球队图片引用；若前端直传，后端先签发限制路径、类型、大小与有效期的授权，再由服务端核验上传结果并绑定。简历没有说明方式，应以实际实现为准。

**追问要点：** 长期 AccessKey 不下发浏览器；使用最小权限和受控凭证。是否公有访问、是否签名预览需单独说明。

### 55 [P0] 上传文件时具体做了哪些校验？只检查扩展名是否足够？

- 追问：大小、实际内容类型、文件名和图片解码异常如何处理？如何避免同名覆盖？

**参考回答：** 同时检查上传大小、扩展名白名单、内容类型和可解码图片特征，必要时重新编码并限制像素尺寸，防止伪装文件和超大图片。Content-Type 由客户端提供，不能单独信任。使用服务端生成的 UUID 等对象名，限制存储路径，不直接拼接用户原始文件名。

**追问要点：** 如支持 SVG，需专门处理可执行内容；失败信息不暴露内部路径和凭证。按实际允许格式回答，不扩大已有实现。

### 56 [P0] OSS 上传成功，但数据库保存 URL 失败怎么办？替换和删除队徽时如何处理旧文件？

- 追问：如何清理孤立文件？保存完整 URL 与保存对象 Key 各有什么维护成本？

**参考回答：** OSS 与 MySQL 通常不在一个事务中，上传成功但绑定失败会产生孤立对象。可以记录上传状态和对象 Key，绑定失败做可重试清理，定期扫描超过保留期仍未绑定的对象。替换时先上传并成功绑定新图片，再异步清理旧对象，避免先删旧图导致页面失效。

**追问要点：** 对象 Key 更利于迁移域名和切换签名地址；简历写保存 URL，就如实说明并把保存 Key 作为改进。清理前确认无引用，避免误删共享资源。

### 57 [P1] 按日期目录管理 OSS 文件解决什么问题？目录与文件唯一标识如何共同设计？

- 追问：私有图片如何预览？临时访问地址过期后前端如何刷新？

**参考回答：** 日期目录便于归档、清理和定位上传批次，本身不保证唯一性，也不等同于访问控制。可用 `club-logo/yyyy/MM/dd/uuid.ext` 这样的结构。私有桶由后端鉴权后生成短期签名地址，前端到期重新申请；数据库保存对象标识，不长期保存会过期的签名 URL。

### 58 [P0] 赛季战绩、球员排行和球员对比的统计口径是什么？

- 追问：跨赛季、并列排名、补赛、缺失数据如何处理？哪些统计由 SQL 完成，哪些交给前端？

**参考回答：** 先约定赛季、比赛状态和统计对象：战绩只算已完成且有效的比赛，胜平负和积分规则按赛事规定，球员排行明确是总量还是场均。后端用 SQL 聚合并返回统一口径的数据，前端只负责展示与交互。缺失数据不随意当成真实零，必要时区分“暂无统计”。

**追问要点：** 补赛按所属赛季计入；并列排名先定义规则。实际使用哪些字段、是否做了去重，应拿真实查询说明。

### 59 [P1] ECharts 图表的接口结构如何设计？没有数据、筛选切换和组件销毁时如何处理？

**追问要点：** 不把不同单位直接混成同一刻度；加载、无数据和失败应分开显示。

### 60 [P1] 训练、伤病与球队日程之间如何关联？如果球员受伤后仍被安排训练，系统如何处理？

## 七 认证 权限与接口安全

### 61 [P0] 两个项目的登录流程分别是什么？JWT 由谁签发、谁校验、有效期如何设置？

- 追问：JWT 包含哪些声明？为什么不能把密码和敏感信息放进去？

**参考回答：** 登录时后端校验凭证，成功后签发带 sub、签发时间、过期时间及必要身份声明的 JWT；请求方携带 Token，服务端验证签名、允许算法、过期及发行者和受众等约束。JWT 常见载荷是编码，不是加密，不能放密码和完整简历。

**追问要点：** 有效期、刷新方式、算法与密钥管理必须按项目实际回答；只解码不验签不构成认证。

### 62 [P0] Spring Security 中，认证和授权分别发生在哪里？请说明你实际配置的过滤链。

- 追问：JWT 校验过滤器如何将身份写入安全上下文？未登录与无权限分别返回什么？

**参考回答：** 安全过滤链先识别凭证，认证成功后建立 Authentication 并写入 SecurityContext，后续根据 URL 或方法权限决定能否访问。JWT 过滤器的位置需结合实际 SecurityFilterChain 配置解释，并处理错误凭证和上下文清理。未认证通常是 401，已认证但无权通常是 403。

**追问要点：** 无状态 API 可按项目策略避免使用服务端 Session；并非所有 Spring Security 项目都需要自己手写 JWT 过滤器。

### 63 [P0] 网关统一认证之后，下游服务如何可信地获得用户身份？

- 追问：如何防止客户端伪造用户 ID 请求头？如果绕过网关直接访问服务会怎样？

**参考回答：** 网关要删除或覆盖客户端传入的身份头，验证 Token 后再注入可信身份；下游还需通过网络访问控制、服务身份验证或自行验证签名，保证请求确实来自可信链路。仅增加 `X-User-Id` 而服务又可被公网直接调用，会出现伪造风险。

**追问要点：** 认证集中不意味着业务授权全部集中。资源归属与操作规则仍应在资源所在服务校验。

### 64 [P0] 角色、菜单权限、操作权限和数据权限分别如何建模？

- 追问：用户权限变更后，已签发 Token 是否仍然有效？如何让权限及时生效？

**参考回答：** 常见 RBAC 是用户关联角色、角色关联权限，菜单用于展示入口，操作权限用于接口动作，数据权限限定可访问的球队、企业或本人记录。权限变更若只依靠旧 JWT 内声明，会持续到过期；可采用短期 Token、权限版本号或服务端状态校验加缓存失效。

**追问要点：** 前端展示权限与后端实际授权必须对应，角色名称不能代替具体资源归属校验。

### 65 [P0] 用户退出登录、修改密码和管理员禁用账号时，如何处理尚未过期的 JWT？

- 追问：是否使用 Redis 保存登录状态或黑名单？采用这种方式后新增了哪些依赖？

**参考回答：** 纯无状态 JWT 在过期前无法仅靠客户端删除而被服务器撤销。需要时可维护 jti 黑名单、账号 Token 版本或在线会话状态，禁用与改密后让校验失败，再配短有效期和刷新凭证策略。退出时清理客户端凭证，并执行实际支持的服务端失效操作。

**追问要点：** 引入 Redis 状态会增加查询、故障处理和一致性成本；需明确 Redis 不可用时是拒绝敏感操作还是采用其他可接受策略，不能默认全部放行。

### 66 [P0] 企业能否查看其他企业收到的简历？求职者能否修改其他人的在线简历？

- 追问：后端如何校验资源归属？哪些接口最容易出现越权？

**参考回答：** 企业只能访问自己发布职位对应的投递，求职者只能操作归属自己的简历。服务端身份来自可信认证结果，查询和更新通过企业或用户范围限定资源，例如简历修改 `WHERE id = ? AND owner_id = ?`。详情、下载、批量接口和聊天记录同样要校验。

**追问要点：** ID 不易猜不是权限保障；即使前端不显示入口，接口也要拒绝越权。

### 67 [P1] 项目如何处理密码存储、SQL 注入、XSS、CSRF 和跨域请求？

- 追问：请分别结合自己的登录方式、SQL 写法和前端展示方式回答，不要只列技术名词。

**参考回答：** 密码使用适合密码存储的带盐自适应哈希，例如 BCrypt，不能明文或普通 MD5。SQL 使用参数绑定；展示用户内容优先文本插值，富文本需过滤；CSRF 风险取决于浏览器是否自动附带凭证，Cookie 登录尤其要防护，手动 Authorization Token 也仍需防范 XSS。跨域配置只允许必要来源、方法和请求头。

**追问要点：** CORS 是浏览器访问策略，不是服务端鉴权；不能用“前后端分离”作为直接关闭所有安全保护的理由。

### 68 [P1] 重复点击提交、恶意高频投递和批量尝试登录，分别应在哪一层处理？



**参考回答：** 重复点击先由前端禁用按钮改善体验，后端由唯一约束或幂等键保证正确性；高频投递按用户、职位和必要的网络维度限流，同时限制异常行为；登录尝试采用限速、失败计数与风险验证，错误提示避免泄露账号存在性。网关可做粗粒度保护，业务服务做业务约束。

## 八 Java 基础 并发与 JVM

### 69 [P1] 结合项目举例说明封装、继承和多态，以及接口与抽象类的选择。



**参考回答：** 封装把投递状态转换与校验放在明确的业务方法中，避免外部任意改字段；继承适合确有“是一个”关系的共性，不为了复用而滥用；多态可用通知发送接口，由站内信、邮件等实现。接口描述能力与契约，抽象类适合共享状态和部分实现；优先组合减少继承耦合。

### 70 [P1] equals 和 hashCode 有什么约定？实体对象作为 HashMap 的 Key 时可能有哪些问题？



**参考回答：** equals 相等的对象必须有相同 hashCode，hashCode 相同不代表 equals 相等；重写通常要同时完成。HashMap 先按哈希定位再比较 Key。Key 若依赖可变字段，放入后修改字段可能导致查不到原项；实体 ID 尚未生成也可能影响相等语义。因此优先选择不可变、稳定的业务键或 ID 作为 Key。

### 71 [P1] ArrayList、HashMap 和 ConcurrentHashMap 分别适合什么场景？

- 追问：HashMap 的冲突和扩容如何处理？多线程共享普通集合有哪些风险？

**参考回答：** ArrayList 适合随机访问和尾部追加，中间插删需要移动元素；HashMap 提供一般键值查找，但不支持并发写入安全；ConcurrentHashMap 支持并发访问及原子组合方法。常见 JDK 8+ HashMap 通过桶、链表及满足条件时的树化处理冲突，负载超过阈值扩容，具体实现随 JDK 版本确认。

**追问要点：** 换成 ConcurrentHashMap 不会让“先查再操作”自动原子，应使用 compute、putIfAbsent 等合适方法，Value 的内部状态也需保护。

### 72 [P0] 你在项目中实际使用过线程池吗？用在哪里？为什么需要异步执行？

- 追问：如果只是学习过，请解释你会如何设计通知发送或批量处理的线程池。

**参考回答模板：** 若实际使用，说明【线程池 Bean、任务入口、参数和监控】；若没有，就直接说“项目主要通过 MQ 解耦，我学习过线程池，但没有承担生产级调优”。设计异步任务时使用受控线程池，给定队列、超时和拒绝策略，记录任务失败，避免无上限新建线程。

**追问要点：** 内存异步任务在进程退出时可能丢失，可靠通知不能只靠 @Async 或普通线程池。

### 73 [P1] ThreadPoolExecutor 的核心参数是什么？任务从提交到被拒绝的完整过程是什么？

- 追问：队列和线程数如何确定？无界队列有什么风险？任务异常如何被发现？

**参考回答：** 核心参数包括 corePoolSize、maximumPoolSize、keepAliveTime、时间单位、workQueue、ThreadFactory 和 RejectedExecutionHandler。一般先建核心线程，核心满后入队，队列满后再扩到最大线程，仍无法接收或池已关闭则拒绝。线程规模依据任务 CPU/等待比例、机器资源和下游容量确定。

**追问要点：** 无界队列可能让任务堆积、延迟和内存失控，maximumPoolSize 也很难发挥作用。execute 的未捕获异常与 submit 封装在 Future 中的异常观测方式不同，应统一监控。参见 [JDK 线程池文档](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ThreadPoolExecutor.html)。

### 74 [P1] synchronized、volatile 和 Lock 各解决什么问题？volatile 能否保证计数递增的原子性？



**参考回答：** synchronized 提供互斥和内存可见性；volatile 保证对该变量的可见性及相关有序性约束，但 `count++` 是读、改、写复合操作，不能因此原子；Lock 提供显式锁定，可按实现支持可中断、超时尝试和多条件等待。简单共享递增可用 AtomicInteger 等原子类。

**追问要点：** Lock 必须在 finally 释放；本地锁只能协调同一进程，不能直接保护多个服务实例的数据库业务。

### 75 [P1] 如何分析线程安全问题？请用“先查后插”或“读出后加一再写回”举例说明竞态。



**参考回答：** 先识别共享状态，再拆开操作的读写步骤，找出可能交错的地方。“先查后插”两个线程可能都看不到记录，必须由唯一约束仲裁；“读出后加一再写回”会覆盖他人更新，应使用原子 SQL、乐观锁或适当加锁。最后用屏障或并发测试放大交错验证。

### 76 [P1] ThreadLocal 适合存储什么？在线程池环境中为何要清理？

- 追问：当前用户信息跨线程或跨服务后还能直接获取吗？

**参考回答：** ThreadLocal 为每个线程保存独立副本，可用于当前请求上下文，但线程池线程会复用，未 remove 可能泄漏旧用户状态或长期占用对象。应在请求结束 finally 中清理。它不会自然跨异步线程或跨服务传播，需显式传递最小上下文，且不可把客户端自报身份当成可信信息。

### 77 [P1] Java 异常体系如何划分？你如何设计业务异常、统一异常处理和错误码？

- 追问：捕获异常后不再抛出，对事务和接口响应可能有什么影响？

**参考回答：** Throwable 下主要有 Error 和 Exception，Exception 中包括受检异常与 RuntimeException。业务异常用稳定业务码表达重复投递、无权限等已知失败，统一异常处理转成一致响应，内部日志保留根因而对外避免暴露堆栈。基础设施异常应分类处理，不能全部包装成功。

**追问要点：** 捕获后不抛出会改变事务拦截器观察到的结果；若内部已标记 rollback-only，即使外层继续返回也可能在提交时报错。

### 78 [P1] IO 流、字符流和字节流有何区别？上传图片时如何管理流和大文件内存占用？



**参考回答：** 字节流处理原始字节，适合图片和文件；字符流按字符集解码，适合文本。使用 try-with-resources 管理自己持有的流，按缓冲流式传输，不把大文件全部读入内存。上传还需限制总大小、单文件大小和时间，并处理临时文件清理。

**追问要点：** UTF-8 等字符集要显式约定；所有权不属于当前方法的框架流，不应不加判断提前关闭。

### 79 [P1] JVM 的主要内存区域各存放什么？对象分配和垃圾回收的基本过程是什么？

- 追问：接口突然变慢时，如何判断是否与频繁 GC、内存增长或线程阻塞有关？

**参考回答：** JVM 常见运行时区域包括堆、线程私有的虚拟机栈与程序计数器、方法区等，HotSpot 中类元数据主要在元空间。对象一般分配在堆上，可达性分析判断是否仍被引用；具体分代、回收与停顿行为依赖所用收集器，不能概括为所有 GC 都一样。

**追问要点：** 对照请求延迟与 GC 日志、堆使用、分配速率和线程栈，区分 GC 停顿、内存泄漏与外部依赖阻塞，不凭“内存高”直接判断泄漏。

### 80 [P2] 线上出现 CPU 持续高、内存持续上涨或线程池耗尽，你分别如何收集证据？



**参考回答：** CPU 高先定位进程和热线程，再匹配线程栈，区分忙循环、热点计算和 GC；内存增长先看堆、堆外及 GC 趋势，必要时比较堆转储中的主要对象与引用链；线程池耗尽看活跃数、队列、拒绝数和线程栈，再查慢 SQL、网络等待或死锁。采集前评估转储开销并保留现场。

## 九 Spring Spring Boot 与 MyBatis

### 81 [P0] Spring IoC 解决什么问题？请结合 Controller、Service、Mapper 的依赖关系说明。

- 追问：为什么选择构造器注入？同一接口有多个实现时如何选择 Bean？

**参考回答：** IoC 把对象创建和依赖装配交给容器，Controller 接收请求，Service 实现业务，Mapper 负责数据库访问，彼此依赖抽象而非到处 new。构造器注入让必需依赖显式、便于测试，也能较早暴露循环依赖。多实现使用 Qualifier 明确选择，或用 Primary 指定默认候选。

### 82 [P1] Bean 的创建与生命周期大致包括哪些阶段？默认作用域下 Bean 是否一定线程安全？



**参考回答：** 大体包括实例化、依赖注入、相关感知回调、初始化前后处理与初始化方法，容器关闭时执行适用的销毁回调；代理可能由后处理器产生。默认 singleton 是容器内共享一个实例，不代表方法或字段自动线程安全。Service 应尽量无请求级可变成员状态，局部变量与受保护的共享资源分清。

### 83 [P0] AOP 的实现思路是什么？项目中事务、日志或权限校验如何使用代理？

- 追问：JDK 动态代理与 CGLIB 有何区别？哪些调用可能不经过代理？

**参考回答：** AOP 把事务、日志等横切逻辑放到拦截流程，由代理在目标方法前后执行增强。JDK 动态代理基于接口，CGLIB 基于生成子类，具体默认选择由框架配置决定。调用必须经过代理才能按代理模式触发增强，同对象内部直接调用通常绕过代理。

**追问要点：** final 方法不能由子类覆盖增强，private 方法不适合按这种方式拦截；不要把任何方法上加注解都视为一定生效。

### 84 [P0] @Transactional 在哪些情况下可能不生效或不按预期回滚？

- 追问：同类内部调用、异常被捕获、异常类型和异步线程分别会带来什么影响？

**参考回答：** 常见原因是对象不是容器 Bean、调用绕过代理、同类自调用、异常被吞掉、回滚规则不匹配、事务管理器或数据源用错。默认常规规则对 RuntimeException 和 Error 回滚，受检异常需要显式规则或已配置的全局策略。异步线程不会直接继承基于当前线程绑定的事务。

**追问要点：** 调整访问性、异常类型和传播方式前先确认实际版本；优先把事务入口放在另一个明确的服务 Bean 上，通过代理调用。参见 [Spring 声明式事务说明](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

### 85 [P0] Spring Boot 自动装配的过程是什么？你如何确认某个配置为什么生效或没有生效？

- 追问：请结合项目实际版本回答，说明条件装配与自定义 Bean 的关系。

**参考回答：** Spring Boot 基于 classpath、已存在的 Bean、属性等条件选择自动配置，并为常见场景提供默认 Bean；自定义 Bean 常可使相应默认配置退让。排查时看依赖、配置属性、条件评估报告，必要时使用 `--debug`。自动配置不是无条件扫描所有类。

**追问要点：** Spring Boot 3 的自动配置候选通常通过 `AutoConfiguration.imports` 声明；较早版本还涉及 spring.factories，不能混用描述。参见 [Spring Boot 自动配置](https://docs.spring.io/spring-boot/reference/using/auto-configuration.html)。

### 86 [P1] Spring MVC 接收到请求后，如何找到 Controller 并完成参数绑定和返回值序列化？

- 追问：参数校验放在哪一层？金额、日期和枚举参数如何校验？

**参考回答：** DispatcherServlet 接收请求，借助 HandlerMapping 找处理器，由 HandlerAdapter 调用 Controller；参数解析、类型转换与校验后执行业务，返回对象通常经消息转换器序列化。DTO 用 Bean Validation 做格式和范围校验，业务层再检查资源归属、状态等业务规则。

**追问要点：** 金额要求正数及允许精度，日期检查范围与先后关系，枚举拒绝非法值；不能只依赖前端校验。

### 87 [P0] MyBatis 的 #{} 与 ${} 有什么区别？动态排序和模糊查询怎样写才安全？



**参考回答：** `#{}` 生成绑定参数，适合值；`${}` 是原样文本替换，外部输入直接进入会有注入风险。列名、排序方向不能简单作为值绑定，应通过后端白名单映射成固定 SQL 片段。模糊查询可绑定已拼好的参数或使用 CONCAT，并按业务决定是否转义 `%` 和 `_`。

**追问要点：** 白名单应映射为可信片段，不能仅做几个字符替换。参见 [MyBatis 参数与 SQL 映射](https://mybatis.org/mybatis-3/sqlmap-xml.html)。

### 88 [P1] MyBatis 的动态 SQL、结果映射和分页在项目中如何使用？

- 追问：一对多查询怎样避免重复数据与 N+1 查询？大列表如何控制返回字段？

**参考回答：** 用 if、where、choose 等组织可选条件，resultMap 处理字段映射和复杂结果，分页通过实际插件或 LIMIT 实现。先确定主记录分页，再批量查询关联数据或采用受控聚合，避免逐条查询产生 N+1。直接在一对多 JOIN 结果上 LIMIT，可能截断主记录或导致 total 不正确。

**追问要点：** 不需要的字段不查，批量 IN 也要控制规模；展示实际 Mapper 和生成 SQL，而不是只描述插件名称。

### 89 [P1] DTO、实体和 VO 各自承担什么职责？为什么接口不能随意直接暴露数据库实体？



**参考回答：** DTO 表达请求或服务间传输契约，实体映射持久化数据，VO 表达前端展示结果。直接暴露实体容易泄露密码哈希、内部状态和审计字段，也会让数据库变化冲击接口。字段转换时显式控制可写字段，避免客户端传入 role、ownerId 等越权修改。

### 90 [P1] 工厂、单例和原型模式分别解决什么问题？请各给出一个适合项目的应用场景。

- 追问：Spring 单例 Bean 与手写单例模式有什么区别？单例对象中保存用户数据有什么风险？

**参考回答：** 工厂集中对象创建和实现选择，适合根据通知类型选择发送器；单例控制实例数量，适合无状态共享组件，但不等于线程安全；原型通过复制已有对象构建新对象，需区分浅拷贝和深拷贝。Spring singleton 是某容器、某 Bean 定义范围内一个实例，不是整个 JVM 必然唯一。

**追问要点：** 单例 Bean 保存“当前用户”会导致请求串数据，应使用方法参数或正确清理的请求上下文。没有实际应用就将场景标明为设计示例。

## 十 MySQL 与 Redis 基础

### 91 [P0] 你会给职位列表、投递记录和财务筛选分别建立什么索引？

- 追问：请先写出实际查询条件、排序和数据分布，再说明联合索引字段顺序。

**参考回答：** 先列高频 SQL。职位可能按状态、地区等过滤并按发布时间排序；投递表需要 `(candidate_id, job_id)` 唯一索引，并按企业查看路径补查询索引；财务常见 `(club_id, deleted, business_date, id)`，若类型过滤很常见，再评估独立索引。等值、范围、排序、选择性和索引宽度共同影响顺序。

**追问要点：** 一个联合索引不可能最优覆盖所有可选条件；不要机械套“区分度高一定放第一”。以真实 SQL、数据分布和执行计划验证。

### 92 [P1] 为什么常见索引使用 B+ 树？聚簇索引、二级索引、回表和覆盖索引有什么关系？



**参考回答：** B+ 树分支节点主要保存导航键，叶子按键有序，较少层数能适应磁盘页访问并支持范围查询。InnoDB 聚簇索引叶子保存整行数据，通常由主键组织；二级索引叶子保存索引列和主键，查询所需列不在索引中时还要按主键回表。覆盖索引可减少回表，但会增加写入与空间成本。

### 93 [P0] 如何使用 EXPLAIN 分析慢 SQL？哪些信息能帮助判断扫描范围和索引选择？

- 追问：有索引为什么仍然可能慢？你会如何验证优化前后的差异？

**参考回答：** 先拿到真实 SQL、参数和数据规模，再看 EXPLAIN 的访问方式、候选及实际索引、估算扫描行数、过滤和额外操作；支持的版本可用 EXPLAIN ANALYZE 看实际耗时与行数，但它会执行语句，要评估影响。有索引仍可能低效，因为范围太大、回表多、排序开销高或锁等待。

**追问要点：** 在相同数据与负载下对比扫描量、耗时分位和负载，不把“出现 Using index”当作唯一优化标准。

### 94 [P1] 深分页为什么可能变慢？职位列表或财务流水如何优化？

- 追问：游标分页对排序字段和翻页体验有哪些要求？

**参考回答：** OFFSET 很大时通常仍需扫描并丢弃前面的记录。可按稳定的 `(business_date, id)` 等排序键做游标分页，用上一页末尾值继续查询；也可先用覆盖索引找主键再取明细，减少回表但不会消除所有偏移扫描。游标适合连续翻页，不天然支持任意跳到第 N 页。

### 95 [P0] 事务的 ACID 是什么？隔离级别、MVCC 和锁分别在解决什么问题？

- 追问：请结合简历实际数据库版本说明，而不是混用不同数据库的行为。

**参考回答：** ACID 分别是原子性、一致性、隔离性和持久性；一致性还依赖正确业务约束。隔离级别定义并发可见性，MVCC 让特定读取使用版本快照，锁约束冲突访问。MySQL InnoDB 常见默认是可重复读，但应查询实际会话配置，不能将默认当作项目事实。

**追问要点：** 本地 ACID 不自动涵盖多个服务或消息系统；读已提交和可重复读的快照建立时机不同。参见 [MySQL 隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。

### 96 [P1] 什么是快照读和当前读？什么情况下可能出现记录锁、间隙锁或临键锁？

- 追问：唯一索引精确查询和范围查询，在不同条件下的加锁范围有什么区别？

**参考回答：** 常见普通一致性 SELECT 是快照读；SELECT FOR UPDATE、更新和删除等会按当前版本与锁规则操作。记录锁保护索引记录，间隙锁约束记录间隙，临键锁结合记录与前方间隙。范围、索引命中情况、记录是否存在和隔离级别会影响加锁范围。

**追问要点：** 在可重复读下，命中存在记录的完整唯一键等值查询通常只需记录锁；缺失键与范围查询不能照此推断，读已提交下间隙锁使用又不同。应在实际版本用并发会话验证。

### 97 [P1] 如何定位死锁？两个业务事务按相反顺序更新数据时，你会怎样改进？



**参考回答：** 从死锁报告与数据库锁等待视图取得冲突事务、SQL、索引和持锁顺序，画出等待环。统一访问顺序、缩短事务、改善索引以减少锁范围，必要时拆分批量操作。数据库回滚受害事务后，可对整个具备幂等性的事务做有限重试，而不是只重放最后一条 SQL。

### 98 [P0] Redis 五种基本数据类型分别是什么？你项目中实际使用了哪些，为什么？

- 追问：字符串、Hash、Set、ZSet 在职位缓存、去重和排行榜中分别适合承担什么职责？

**参考回答：** String 适合 JSON 职位缓存和计数，Hash 适合按字段保存对象，List 适合有序列表操作，Set 适合无序去重成员集合，ZSet 按分值排序，适合排行榜。选择取决于访问模式，不是五种都必须用上；项目若只用了 String，就明确说明。

**追问要点：** Set 去重不能代替数据库永久唯一约束；分数相同时需明确排名规则，排行榜业务事实也应可恢复。

### 99 [P1] RDB 和 AOF 的主要区别是什么？如果 Redis 只用于缓存，持久化应如何取舍？



**参考回答：** RDB 周期性生成快照，恢复路径较简单，但最近变更可能不在快照中；AOF 记录写命令，数据丢失窗口与刷盘策略有关，日志重写用于控制体积。可以组合使用，实际开销和恢复速度需验证。若纯缓存且可受控重建，可按业务成本降低持久化需求，但重启后的冷启动回源压力要考虑。

**追问要点：** 不承诺 AOF 绝对零丢失，持久化也不能取代备份和高可用设计。

### 100 [P1] Key 过期与内存淘汰有什么区别？大 Key 和热点 Key 会带来什么问题？



**参考回答：** 过期是数据达到 TTL 后不再有效，Redis 结合访问检查和周期清理等机制移除；淘汰是在内存达到阈值时按策略选择键移除或拒绝写入。大 Key 会增加传输、处理、删除及内存管理成本，热点 Key 会集中流量。应限制单值大小、拆分或分页，结合本地短缓存与受控复制等分流，并监控失效风暴。

### 101 [P2] Redis 锁与数据库唯一约束分别能保障什么？防重复投递为何仍需要数据库兜底？



**参考回答：** Redis 锁主要减少并发执行和重复重建，受租期、网络及故障切换影响；数据库唯一约束在最终写入点维护不可重复事实。防重复投递即使加了分布式锁，仍可能因为锁过期等原因发生重叠执行，因此必须有数据库约束兜底。锁是协作手段，唯一约束是数据不变量，二者职责不同。

### 102 [P0] Vue 3 中 ref、reactive、computed 和 watch 分别用于什么场景？

- 追问：请用财务筛选表单或赛季统计页面举例说明，为什么不把所有逻辑都放进 watch？

**追问要点：** 异步 watch 注意旧请求清理与时序；computed getter 应避免副作用。参见 [Vue 响应式基础](https://vuejs.org/guide/essentials/reactivity-fundamentals.html)。

### 103 [P1] Vue 组件间如何通信？列表、编辑弹窗和详情组件之间的数据如何组织？

**追问要点：** 不把所有状态都放到全局，避免页面离开后残留筛选和编辑数据。

**参考回答：** 用表单规则校验必填、格式和范围，提交前显式等待校验；提交期间设置 loading 并阻止重复操作，finally 恢复状态。后端仍需业务校验和幂等。失败时保留输入并提示明确原因，成功后关闭弹窗刷新；删除导致当前页为空时，回退到有效页码再查询。

### 105 [P0] 前端登录态、菜单和按钮权限如何管理？页面刷新后如何恢复？

**追问要点：** 不自动重放不具备幂等性的写请求；敏感授权以服务端为准。

### 106 [P1] JavaScript 事件循环、Promise 和 async/await 的基本执行顺序是什么？

- 追问：并行加载列表和统计数据如何组织？其中一个失败时页面应该怎样表现？

**参考回答：** JavaScript 当前同步任务先执行，Promise 回调等微任务在适当检查点处理，再进入后续任务；async 函数执行到 await 挂起后，后续逻辑以异步续体继续，不会把同步计算变成后台线程。互不依赖的列表和统计请求可以并发，独立展示可用 allSettled 或分别捕获异常，允许部分成功。

**追问要点：** 一段耗时同步代码仍会阻塞交互；Promise.all 某个失败不会自动取消其他请求。

### 107 [P1] Ajax 是什么？jQuery 请求与 Vue 项目中实际使用的请求方式有哪些共同点和区别？

- 追问：请求拦截器、响应拦截器、超时与取消请求分别在哪里配置？

**参考回答：** Ajax 是浏览器异步请求并更新局部页面的方式，不等同于某个库。jQuery.ajax、fetch 或 Axios 都可完成网络交互，但接口和默认行为不同。Vue 项目通常封装请求实例，统一 baseURL、认证头、超时和响应错误转换；取消依具体客户端使用 AbortController 等机制。

**追问要点：** 请求拦截器做公共处理，业务分支留在业务代码；fetch 对 HTTP 4xx/5xx 通常仍需显式检查 response.ok，不能照搬其他库行为。

### 108 [P0] 前后端联调时出现 400、401、403、404、500 或跨域错误，你分别如何定位？

**参考回答：** 400 看参数和校验信息；401 看凭证是否缺失、失效或未正确附带；403 看操作和资源权限；404 核对前缀、网关重写及后端映射；500 用请求标识查后端根因。跨域先看预检与响应头，确认实际来源、方法、凭证和代理配置，不能把所有网络错误都归为 CORS。

**追问要点：** 在网络面板核对完整 URL、请求体、Content-Type、响应码与耗时，必要时脱敏复制请求复现。

### 110 [P1] 大列表、大图表或频繁输入筛选导致页面卡顿时，你如何定位和优化？

- 追问：防抖与节流有什么区别？哪些优化应由后端分页或接口设计承担？

**参考回答：** 先用性能工具区分脚本执行、布局绘制、网络和大数据处理。列表后端分页，确有需要再虚拟滚动；图表减少数据点和重复初始化；输入查询用防抖并取消旧请求。防抖等待连续触发结束再执行，节流限制一段时间内执行频率。大数据聚合尽量由后端完成。

**追问要点：** 性能优化应测量前后差异，不因数据少时看起来流畅就断言能承载大规模。

**参考回答：** 以下伪代码侧重受控重建，不承诺跨故障的强一致缓存。退避有上限，回源有独立容量预算。

```text
getJob(id):
    validateId(id)
    deadline = requestDeadline()
    try:
        repeat within deadline and boundedAttempts:
            value = redis.get(cacheKey(id))
            if value == NULL_MARKER: return notFound
            if value exists: return decode(value)

            token = randomUniqueToken()
            locked = redis.set(lockKey(id), token, NX, PX, lockTtl)
            if not locked:
                boundedBackoff()
                continue

            try:
                value = redis.get(cacheKey(id))  // 二次检查
                if value exists: return decodeOrNotFound(value)
                job = readDatabaseWithBulkheadAndTimeout(id)
                payload = encode(job) or NULL_MARKER
                ttl = job ? normalTtlWithJitter : shortNullTtl
                // 同一 Redis 节点执行 Lua：仍持有锁才写缓存。
                // 集群需安排相关 key 同槽，例如使用 {jobId} hash tag。
                atomicCacheWriteIfLockTokenMatches(lockKey, token,
                                                   cacheKey, payload, ttl)
                return job or notFound
            finally:
                bestEffortUnlockByToken(lockKey, token)
        return busy
    catch RedisConnectionOrTimeout:
        recordCacheFailure()
        return readDatabaseWithBulkheadAndTimeout(id)
```

-- 原子释放锁；KEYS[1] 为锁键，ARGV[1] 为本次持有者 token。

### 129 [P1] 用 Java 完成一个基础数据处理题，例如合并区间、统计高频元素或实现 LRU 缓存。

- 要求：先确认输入边界，再解释时间与空间复杂度，并构造空输入、重复值和极端值用例。

**参考回答：** 以合并区间为例，先按左端点排序，再维护当前合并区间。这里约定闭区间，端点相接也合并；合法输入满足 start <= end。输入复制后排序，避免修改调用方数组。

```java
import java.util.*;

public class IntervalMerger {
    public static int[][] merge(int[][] intervals) {
        if (intervals == null || intervals.length == 0) {
            return new int[0][];
        }
        int[][] a = new int[intervals.length][2];
        for (int i = 0; i < intervals.length; i++) {
            if (intervals[i] == null || intervals[i].length != 2
                    || intervals[i][0] > intervals[i][1]) {
                throw new IllegalArgumentException("invalid interval");
            }
            a[i] = intervals[i].clone();
        }
        Arrays.sort(a, Comparator.comparingInt(x -> x[0]));
        List<int[]> result = new ArrayList<>();
        int left = a[0][0], right = a[0][1];
        for (int i = 1; i < a.length; i++) {
            if (a[i][0] <= right) {
                right = Math.max(right, a[i][1]);
            } else {
                result.add(new int[]{left, right});
                left = a[i][0];
                right = a[i][1];
            }
        }
        result.add(new int[]{left, right});
        return result.toArray(new int[0][]);
    }
}
```

**复杂度与用例：** 时间 O(n log n)，包含复制与结果的额外空间 O(n)。测试空数组、单区间、重复、嵌套、不相交、相接、负数及整数端点极值；比较器不用相减，避免整数溢出。若题目要求半开区间，端点合并规则需重新约定。
