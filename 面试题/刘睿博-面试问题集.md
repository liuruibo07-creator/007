## 一、Java 基础与核心技术（3 题）

### Q1. 你简历里写了「熟悉 Java 集合框架」，那 HashMap 的底层实现你能讲讲吗？

**问题**：请说明 JDK 8 中 HashMap 的数据结构（数组 + 链表 / 红黑树）、扩容机制，以及为什么在链表长度达到 8 时会转成红黑树、扩容时又是如何重新散列的。再谈谈多线程环境下 HashMap 可能出现什么问题，为什么推荐使用 ConcurrentHashMap。

> **考察点**：核心数据结构掌握的深度，是否理解"为什么这样设计"而不仅仅是"是什么"。

**参考答案**：

- **数据结构**：JDK 8 的 HashMap 是「数组 + 链表 + 红黑树」。数组是主干（桶），每个桶里挂链表或红黑树。
- **定位过程**：`put` 时先对 key 的 `hashCode()` 做扰动（高 16 位与低 16 位异或，让高位也参与定位），再 `(n-1) & hash` 算出桶下标。
- **链表转红黑树**：当链表长度达到 8 且数组容量 ≥ 64 时，链表转红黑树（若数组还小，会优先扩容而不是树化）。原因是链表查找是 O(n)，红黑树是 O(log n)，长度大了之后树更优。
- **为什么是 8**：源码注释依据泊松分布计算，当负载因子为 0.75 时，一个桶里链表长度到 8 的概率大约只有千万分之六，非常罕见，说明此时大概率是 hash 设计有问题或遭遇了攻击，需要树化兜底。
- **红黑树退化**：树节点数 ≤ 6 时转回链表。
- **扩容**：默认容量 16、负载因子 0.75，超过阈值扩容为原来的 2 倍。扩容后每个元素用 `hash & oldCap` 判断高位，等于 0 留在原位置，否则移到「原位置 + oldCap」，避免了重新计算 hash。
- **多线程问题**：JDK 7 头插法在并发扩容时会形成环形链表导致死循环；JDK 8 改成尾插法避免了死循环，但仍会丢数据（两个线程同时 put，覆盖彼此结果）。
- **ConcurrentHashMap**：JDK 8 用 CAS + `synchronized` 锁单个桶头节点 + `volatile` 保证可见性，读写并发度比整个表加锁高得多。

### Q2. 简历提到「线程池」，你用过 `ThreadPoolExecutor` 的哪些参数？核心线程数一般怎么设定？

**问题**：请解释核心线程数、最大线程数、存活时间、工作队列、拒绝策略这几个参数的含义，以及任务提交后线程池的执行流程。如果是 CPU 密集型和 IO 密集型任务，核心线程数分别怎么估算？

> **考察点**：并发基础是否扎实，能否把参数设计与业务场景联系起来。

**参考答案**：

- **核心参数**：
  - `corePoolSize` 核心线程数：常驻线程数；
  - `maximumPoolSize` 最大线程数；
  - `keepAliveTime` + `unit`：非核心线程空闲多久被回收；
  - `workQueue` 工作队列：核心线程忙时任务先进队列；
  - `threadFactory` 线程工厂：自定义线程命名、是否守护线程等；
  - `handler` 拒绝策略：队列满且线程数达最大值时怎么处理。
- **执行流程**：提交任务 → 核心线程数未满则建核心线程执行 → 核心线程都忙则入队 → 队列满了才创建非核心线程 → 达到最大线程数仍处理不过来则触发拒绝策略。
- **四种拒绝策略**：`AbortPolicy`（抛异常，默认）、`CallerRunsPolicy`（交给提交任务的线程执行，有削峰作用）、`DiscardPolicy`（静默丢弃）、`DiscardOldestPolicy`（丢弃队列最旧任务）。
- **线程数估算**：
  - CPU 密集型：`CPU 核数 + 1`，避免线程切换浪费；
  - IO 密集型：`CPU 核数 × 2`（或 `核数 / (1 - 阻塞系数)`），让 CPU 在等待 IO 时也能被其他线程利用。

### Q3. 你了解设计模式，简历里写的是「工厂、原型、单例」。单例模式有哪些写法，分别有什么优缺点？

**问题**：请列举懒汉式、饿汉式、双重检查锁、静态内部类、枚举等实现方式，并说明双重检查锁为什么要加 `volatile`。如果让你在 Spring 里"保证某个 Bean 全局只有一个实例"，和手写单例有什么区别？

> **考察点**：设计模式理解是否到位，能否联系 Spring 的 Bean 作用域，避免背答案。

**参考答案**：

- **常见写法与对比**：
  - **饿汉式**：类加载时就创建实例，线程安全但可能造成浪费（没用到也创建了）；
  - **懒汉式**：用到才创建，普通写法线程不安全；
  - **双重检查锁（DCL）**：第一次判空避免每次都加锁，加锁后二次判空避免重复创建，兼顾性能与安全；
  - **静态内部类**：利用类加载机制保证线程安全且懒加载，推荐；
  - **枚举**：JVM 保证线程安全、能天然防止反射和反序列化破坏单例，是《Effective Java》推荐的最优方式。
- **DCL 为什么加 `volatile`**：`new` 一个对象不是原子操作，分为「分配内存 → 初始化对象 → 引用指向内存」三步，可能被指令重排。若不加 `volatile`，另一个线程可能拿到「引用已赋值但对象还没初始化完」的半成品实例，读到错误数据。`volatile` 禁止了这种重排。
- **与 Spring Bean 的区别**：Spring 的 `@Bean` 默认作用域就是 `singleton`，但它是"每个 IOC 容器一个实例"，由容器统一管理生命周期、依赖注入，与手写单例"进程内全局唯一"的语义略有不同。所以工程里通常直接用 Spring 的单例作用域，而不需要自己写单例类。

## 二、Spring 全家桶（3 题）

### Q4. 你写"理解 Spring 的 IOC 和 AOP"，能说说 IOC 解决了什么问题吗？Bean 的生命周期大致是怎样的？

**问题**：请用自己的话解释"控制反转"和"依赖注入"，并描述一个 Bean 从创建到销毁的完整生命周期。AOP 底层用的是 JDK 动态代理还是 CGLIB？分别在什么场景下生效？

> **考察点**：框架理解是否停留在"会用注解"，还是真正懂底层机制。

**参考答案**：

- **IOC（控制反转）**：把"对象由谁创建、依赖由谁注入"的控制权从程序员手里交给容器。以前是自己 `new`，现在声明一下，容器帮你创建并注入。**DI（依赖注入）**是 IOC 的一种实现方式。
- **解决的核心问题**：解耦。对象之间不直接依赖具体实现，而是依赖抽象，改实现只需改配置/注解，不用改业务代码。
- **Bean 生命周期**：实例化 → 属性填充（依赖注入）→ 各种 `Aware` 接口回调（如 `BeanNameAware`、`BeanFactoryAware`）→ `BeanPostProcessor#postProcessBeforeInitialization` → `@PostConstruct` / `InitializingBean#afterPropertiesSet` → `BeanPostProcessor#postProcessAfterInitialization` → 使用 → `@PreDestroy` / `DisposableBean#destroy` 销毁。
- **AOP 代理**：
  - 目标类实现了接口 → 默认用 **JDK 动态代理**（基于接口，生成一个实现相同接口的代理类）；
  - 目标类没有接口（或强制指定）→ 用 **CGLIB**（基于继承，生成目标类的子类）。
  - Spring Boot 2.x 起 `spring.aop.proxy-target-class` 默认是 `true`，所以基本都走 CGLIB。

### Q5. Spring Boot 的自动装配原理你能讲一下吗？

**问题**：请从 `@SpringBootApplication` 出发，说明 `@EnableAutoConfiguration`、`spring.factories` / `AutoConfiguration.imports`、条件注解是如何协作，让框架"开箱即用"的。有没有自己封装过 starter 或踩过自动装配的坑？

> **考察点**：是否知其所以然，能否排除"自动装配失效"这类常见问题。

**参考答案**：

- `@SpringBootApplication` 是一个组合注解，包含 `@SpringBootConfiguration`、`@EnableAutoConfiguration`、`@ComponentScan`。
- 核心是 `@EnableAutoConfiguration`，它通过 `@Import(AutoConfigurationImportSelector.class)` 导入自动配置类。
- 这个 Selector 会读取 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件（老版本是 `spring.factories` 里的 `EnableAutoConfiguration` 项），得到一堆自动配置类列表，再逐个加载。
- 这些配置类上大量使用**条件注解**决定要不要生效：`@ConditionalOnClass`（classpath 里有某个类才生效）、`@ConditionalOnMissingBean`（容器里没有这个 Bean 才创建）、`@ConditionalOnProperty`（配置项满足条件才生效）等。正是这些条件注解让"引入依赖就自动配置、不引入就不配"成为可能。
- **常见坑**：自己定义的同名 Bean 被 `@ConditionalOnMissingBean` 判断后，自动配置就不再生效；或者 classpath 里缺某个依赖导致自动配置悄悄不生效，排查时可以开 `--debug` 看条件评估报告。

### Q6. 你项目里用了 Spring MVC 和 JWT 做认证，一个请求从进入前端控制器到返回响应的完整流程是怎样的？

**问题**：请描述 `DispatcherServlet` 的处理链路，并说明在你的项目里，JWT 鉴权是放在过滤器还是拦截器实现的？为什么这么选？

> **考察点**：Web 层原理 + 认证方案落地细节，检验真实开发经验。

**参考答案**：

- **处理链路**：请求进入 `DispatcherServlet` → `HandlerMapping` 找到对应的 Handler（Controller 方法）→ `HandlerAdapter` 负责调用 → 执行拦截器 `preHandle` → 参数解析（如 `@RequestBody` 用消息转换器）→ 调用 Controller → 返回结果 → 拦截器 `postHandle` / `afterCompletion` → 视图解析或消息转换输出响应。
- **JWT 放哪**：
  - **过滤器（Filter）**：属于 Servlet 规范，在进入 Spring 之前就执行，适合做"全局统一"的认证——尤其是**网关**这种所有请求都经过的地方。
  - **拦截器（Interceptor）**：属于 Spring 范畴，能拿到 Handler 信息，方便做细粒度的按方法放行。
- **结合项目**：招聘平台是微服务，认证放在**网关的全局过滤器**里统一做（`UserLoginGlobalFilter` 解析 token、校验、把 `userId`/`role` 透传到下游），各下游服务再用拦截器（`UserInfoInterceptor`）把透传过来的用户信息写入 `ThreadLocal`，业务层直接取用，避免每个服务重复解析 token。

## 三、数据库与缓存（4 题）

### Q7. 简历写"理解 MySQL 事务"，事务的 ACID 和四种隔离级别能讲清楚吗？MVCC 是如何实现可重复读的？

**问题**：请说明四种隔离级别分别解决/遗留哪些问题，并解释 InnoDB 是如何通过 Undo Log + Read View 实现 MVCC 的。你在项目里遇到过的并发事务问题是怎么定位和解决的？

> **考察点**：事务原理的深度，以及是否有真实的问题排查经历。

**参考答案**：

- **ACID**：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。
- **四种隔离级别**：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 Read Uncommitted | ✗ | ✗ | ✗ |
| 读已提交 Read Committed | ✓ | ✗ | ✗ |
| 可重复读 Repeatable Read（MySQL 默认） | ✓ | ✓ | 大部分解决（靠间隙锁） |
| 串行化 Serializable | ✓ | ✓ | ✓ |

- **MVCC 原理**：InnoDB 每行记录有隐藏列（事务 ID、回滚指针），更新时旧版本链在 **Undo Log** 上形成版本链。事务开启时生成一个 **Read View**（记录当前活跃事务集合），读取时从版本链里找到对当前事务可见的那个版本，从而实现不加锁的"快照读"，这就是可重复读的由来。
- **可重复读下的幻读**：MVCC 快照读解决了大部分幻读，但当前读（如 `SELECT ... FOR UPDATE`）仍有幻读，InnoDB 用**间隙锁（Gap Lock）+ 临键锁（Next-Key Lock）**锁住索引区间来杜绝。
- **项目经验**：比如"防止重复投递"这种场景，光靠业务判断（先查再插）在并发下会失效，两个请求同时查到"没投递过"然后都插入成功。解决办法是加**唯一索引**兜底 + 事务保证。

### Q8. 你项目里做了分页查询和条件聚合，慢查询你是怎么优化的？

**问题**：请谈谈你是如何判断一条 SQL 慢的（`EXPLAIN` 关注哪些字段），索引失效的常见场景有哪些，以及你在财务汇总接口里对聚合查询做过哪些优化。

> **考察点**：SQL 优化实战能力，能否讲出具体字段和具体优化动作。

**参考答案**：

- **EXPLAIN 关注字段**：
  - `type`：访问类型，从优到劣 `const > eq_ref > ref > range > index > ALL`，出现 `ALL`（全表扫描）基本就要优化；
  - `key`：实际用到的索引，空说明没走索引；
  - `rows`：预估扫描行数，越大越慢；

- **聚合优化思路**：给条件列（如时间、用户）建合适的联合索引；只查需要的列避免 `SELECT *`；统计类查询可以缓存（项目里职位/投递统计用 Redis 缓存 60 秒，避免高频聚合打库）；金额运算统一用 `BigDecimal` 避免精度问题。

### Q9. Redis 的持久化机制（RDB 和 AOF）有什么区别？你项目里 Redis 挂了怎么办？

**问题**：请对比 RDB 和 AOF 的优缺点、触发方式和恢复速度，说说生产环境一般怎么搭配。结合你的简历，你写了"Redis 异常时降级查询数据库"，这个降级逻辑具体是怎么实现的？

> **考察点**：缓存高可用意识，以及"降级"是否真的落到代码上而非纸上谈兵。

**参考答案**：

- **RDB**：定时把内存快照写盘（`save`/`bgsave`），恢复快、文件小，但两次快照之间宕机会丢最近的数据。
- **AOF**：每次写操作追加日志，`always`/`everysec`/`no` 三种刷盘策略，数据更完整但文件大、恢复慢。
- **生产搭配**：一般 **RDB + AOF 一起开**，或使用 Redis 4.0+ 的**混合持久化**（AOF 里存 RDB 快照 + 增量命令），兼顾恢复速度和数据完整性。
- **降级实现**：项目里封装了 `RedisUtil`，**所有方法内部 `try-catch`**：`get`/`increment` 异常时返回 `null`（调用方回退查库），`setIfAbsent` 异常时返回 `true`（放行业务，不因缓存故障拦截请求）。这就是"缓存是旁路增强，Redis 故障绝不阻塞主流程"的设计理念——缓存挂了，系统只是慢，而不是不可用。

### Q10. 你简历里写了缓存穿透、缓存雪崩、缓存击穿，能不能分别讲清楚它们的定义和你的解决方案？

**问题**：请解释三者的区别，并详细说明你在招聘平台项目里"空值缓存、缓存重建互斥锁、随机过期时间"分别对应解决哪个问题、具体代码是怎么写的。再补充一下：分布式锁你是怎么实现的，用 Redis 的什么命令？

> **考察点**：缓存三大经典问题的精确理解 + 分布式锁实现细节，是这份简历的高频深挖点。

**参考答案**：

- **三个问题的区别**：
  - **缓存穿透**：查询一个**根本不存在**的数据，缓存和 DB 都没有，请求直接打穿缓存压到 DB（往往是恶意攻击）。→ 解决：**空值缓存**（把"不存在"也缓存成空串，短 TTL）、布隆过滤器。
  - **缓存击穿**：某个**热点 key** 在过期的瞬间，大量请求同时打到 DB。→ 解决：**互斥锁重建**（`setnx` 加锁，拿到锁的请求去回源回填，其他请求等待/重试）、逻辑过期。
  - **缓存雪崩**：**大量 key 同时过期**（或 Redis 宕机），请求集中打到 DB。→ 解决：**随机过期时间**（TTL 加随机抖动）、多级缓存、限流。
- **结合项目代码**（职位信息缓存 `getJobInfoCached`）：
  - 空值缓存：职位不存在时，用空串 `""` 缓存，区分"没查到"和"查到了但为 null"，避免每次穿透；
  - 互斥锁防击穿：`setIfAbsent(key + ":lock", "1", 5s)` 拿锁，拿到锁的请求回源查询回填，其他请求 `Thread.sleep(60ms)` 后重试读缓存；
  - 随机过期防雪崩：TTL 用 `10 分钟 + RandomUtil.randomInt(0, 3)` 分钟抖动，避免同一批 key 同时过期。
- **分布式锁命令**：用 `SET key value NX EX seconds`（Spring 里 `opsForValue().setIfAbsent(key, value, ttl)`），保证"加锁"和"设过期时间"两步原子完成。项目里还做了异常降级：`setIfAbsent` 失败时返回 `true` 放行，保证 Redis 挂了不阻塞业务。

## 四、微服务与分布式（4 题）

### Q11. 你用了 Nacos 做注册中心和配置中心，Nacos 的心跳机制和服务发现流程是怎样的？

**问题**：请说明服务提供者如何注册、消费者如何拉取服务列表、Nacos 如何剔除不健康实例，以及配置中心如何实现配置的动态刷新。和 Eureka、Consul 相比，你为什么会选 Nacos？

> **考察点**：注册中心原理，能否讲出技术选型的理由。

**参考答案**：

- **注册**：服务启动时向 Nacos 注册自己的 IP、端口、健康状态等元信息。
- **心跳/健康检查**：Nacos 支持**临时实例**（客户端 5 秒一次心跳，15 秒没收到心跳就标记不健康，30 秒移除）和**持久实例**（服务端主动探测）。
- **服务发现**：消费者启动时从 Nacos 拉取服务列表并缓存到本地，之后通过 **UDP 推送 + 定时轮询（如 10 秒）** 感知实例变化。
- **配置中心**：客户端启动时拉取配置，长轮询监听变更，配置更新后客户端动态刷新（配合 `@RefreshScope`）。
- **选型理由**：Nacos 一个组件同时做**注册中心 + 配置中心**，功能整合度高；相比 Eureka（2.x 已停更、只做注册）、Consul（偏重 CP，强一致写入性能差），Nacos 的 AP/CP 可切换更灵活，且原生支持配置管理和灰度，与 Spring Cloud Alibaba 生态契合。

### Q13. OpenFeign 的底层原理你了解吗？调用一个远程接口时发生了什么？

**问题**：请解释 OpenFeign 如何通过动态代理把接口方法转成 HTTP 请求，负载均衡是如何协作的，以及你在联调时遇到过的超时、序列化、熔断等问题是怎么处理的。

> **考察点**：RPC 调用链路理解，检验微服务联调的真实经验。

**参考答案**：

- **原理**：OpenFeign 通过 **JDK 动态代理**，把加了 `@FeignClient` 的接口生成一个代理对象。调用接口方法时，代理对象根据方法上的注解（`@GetMapping`、`@RequestParam`、`@RequestBody` 等）拼出 HTTP 请求，再由 `Client`（如 OkHttp/HttpClient）真正发出请求，拿到响应后按返回类型反序列化。
- **负载均衡**：请求发出前，`@FeignClient` 的 `name` 会被 Spring Cloud LoadBalancer 解析成实际的服务实例列表，从中选一个实例发起调用（默认轮询）。
- **联调常见问题**：
  - **超时**：配置 `connectTimeout`/`readTimeout`，或全局 `feign.client.config.default`；
  - **序列化**：跨服务传递的对象（DTO）要保证两端的类结构一致，或用统一的公共模块（项目里抽了 `cloud-model`）；
  - **服务降级**：配合 `fallback` 在远程调用失败时给默认值。项目里列表页对远程职位查询失败时静默降级返回 null，不拖垮主流程。

### Q14. 你用了 Seata 保证跨服务数据一致性，能讲讲 Seata 的 AT 模式原理吗？什么场景下你会选消息最终一致性？

**问题**：请描述 AT 模式的两阶段提交过程（全局锁、Undo Log、回滚机制），并结合你的投递链路说明：为什么"投递记录 + 职位投递数"需要分布式事务，而"投递后发送通知"却用了 RabbitMQ 做最终一致性？这两者的边界你是怎么拿捏的？

> **考察点**：分布式事务方案选型，能否分清"强一致"与"最终一致"的适用场景。

**参考答案**：

- **AT 模式（两阶段）**：
  - **一阶段**：各服务正常执行本地事务，同时把修改前后的数据写入 **Undo Log**（用于回滚）；
  - **提交**：全局事务协调器（TC）确认所有分支都成功，删除 Undo Log；
  - **回滚**：任一分支失败，TC 通知各分支用 Undo Log 反向补偿，把数据改回去。
  - XID（全局事务 ID）通过 Feign 拦截器在服务间透传，让下游服务的本地事务注册为同一个全局事务的分支。
- **强一致 vs 最终一致的选择**：
  - **投递记录 + 职位投递数**：这两者是同一个"投递"动作的两面，必须**强一致**——不能出现"投递成功但投递数没加"或"投递数加了但投递记录没写"。所以用 Seata 全局事务保证。
  - **投递后发通知**：通知是异步的、可以稍后到达的，不要求立刻一致。用 RabbitMQ 解耦后，投递接口不用同步等待通知生成，吞吐更高。所以用**消息最终一致性**。
- **拿捏边界的原则**：**核心业务数据（影响钱、影响用户可感知的结果）用强一致；可以延迟、可以重试的旁路操作（通知、统计、日志）用最终一致**。

### Q17. 足球俱乐部管理系统里，财务汇总接口为什么用 `BigDecimal` 处理金额？如果用了 `double` 会有什么问题？

**问题**：请解释浮点数精度丢失的根本原因（二进制无法精确表示十进制小数），以及 `BigDecimal` 使用时的注意点（构造方法选 `String` 而非 `double`、`compareTo` 与 `equals` 的区别、舍入模式）。你在前后端之间金额是用什么类型传输的？

> **考察点**：财务场景的严谨性，是简历里明确写出、面试官最容易顺着问的点。

**参考答案**：

- **为什么不能用 `double`**：浮点数用二进制近似表示十进制小数，很多十进制小数（如 `0.1`）在二进制里是无限循环的，存储会有误差。例如 `0.1 + 0.2` 在 `double` 下结果不是精确的 `0.3`。财务金额对精度要求极高，累积误差不可接受。
- **`BigDecimal` 注意点**：
  - 构造方法用 `new BigDecimal("0.1")`（字符串）而不是 `new BigDecimal(0.1)`（double），后者会把 double 的误差带进来；
  - 比较大小用 `compareTo`（比较数值，`0.10` 和 `0.1` 相等），不要用 `equals`（它连标度 scale 也一起比较，`0.10` 和 `0.1` 会判为不等）；
  - 加减乘除指定舍入模式（`divide` 不指定舍入模式，除不尽会抛 `ArithmeticException`）。
- **前后端传输**：金额在后端用 `BigDecimal` 计算，前端展示时通常转成字符串（避免 JS 的 `number` 精度问题，前端可用 `json-bigint` 或直接用字符串），保证端到端精度一致。

### Q18. 队徽上传你是怎么接入阿里云 OSS 的？"日期目录管理 + URL 持久化到 MySQL"具体怎么设计的？

### Q19. 在线招聘平台里，一次"投递简历"涉及了哪些步骤？你是怎么防止重复投递的？

**问题**：请结合你的投递接口（`submitApplication`）讲清楚完整链路，重点说明你为"防止重复投递"设计了哪几道防线，每一道分别解决什么问题，为什么少了任何一道都可能出问题。

> **考察点**：这是候选人简历中"唯一索引防重复投递"的具体落地，考察对并发场景下"先查再插"失效的深刻理解。

**参考答案**：

- **完整投递链路**：参数校验 → 登录与角色校验（只有求职者可投）→ 简历归属校验（必须是本人简历）→ 远程校验职位存在且招聘中 → 写投递记录 → 远程递增职位投递数（Seata 全局事务）→ 事务提交后发 MQ 通知企业。
- **防重复投递的三道防线**：
  1. **Redis 防连点锁**（`setIfAbsent`，TTL 10 秒）：同一用户对同一职位 10 秒内只允许提交一次，挡住手抖连点/重复提交风暴；
  2. **先查后插的友好提示**（`countByUserAndJob` 查一次）：给用户"已投递过"的友好提示，而不是让用户撞数据库异常；
  3. **数据库唯一索引 `uk_user_job`（user_id, job_id）兜底**：这是**最终正确性保证**。因为前两道防线在并发下都可能失效——两个请求同时通过"先查再插"的检查，都执行插入。唯一索引在数据库层硬性拦截，第二个插入会失败，保证绝不会产生重复投递记录。
- **为什么缺一不可**：防连点锁是性能优化（挡掉大部分无效请求），唯一索引是正确性兜底（并发下唯一可靠的防线）。如果只有"先查再插"没有唯一索引，高并发下一定会产生重复数据。

### Q20. 你投递接口里，MQ 消息为什么要"事务提交后才发送"？如果消息发送失败了怎么办？

**问题**：请解释你代码里用 `TransactionSynchronization` 在 `afterCommit` 阶段发消息的原因，以及为了保证消息可靠性，你在生产端和消费端分别做了哪些设计？

> **考察点**：考察"本地事务与消息"的一致性问题、消息可靠投递机制，是简历中"消息重试及异常消息队列"的落地细节。

**参考答案**：

- **为什么 afterCommit 发**：如果写完投递记录后立即发 MQ，但发完之后本地事务回滚了，就会出现"通知已经发出、但投递记录其实没落库"的脏消息。所以把发消息挂到**事务同步器**的 `afterCommit` 回调里，**事务真正提交成功后才发消息**，从根上避免"事务回滚了消息却发了"。
- **生产端可靠性**：
  - 消息**持久化**（`DeliveryMode.PERSISTENT`），Broker 重启不丢；
  - **ConfirmCallback**：确认消息是否真正到达 Broker，没到则记日志（`TODO` 注释里预留了"写入本地消息表 + 定时任务补偿重发"的方案）；
  - **ReturnsCallback**：消息路由不到队列时（`mandatory=true`）回调而不是被静默丢弃；
  - 用 `Jackson2JsonMessageConverter` 跨服务 JSON 传输，避免 JDK 序列化要求两端类名包名一致。
- **消费端可靠性**：
  - 自动 ACK + 本地重试（重试 3 次，指数退避）；
  - 全部失败后由 `RepublishMessageRecoverer` 把消息转发到**错误队列**（`error.direct -> error.queue`），人工/定时任务兜底处理，保证消息不丢失。
- **本质**：这是"本地消息表 / 可靠消息最终一致性"思想的简化实现——事务内保证业务和消息的一致性，事务外保证消息不丢。

### Q21. 你的职位搜索为什么用 Elasticsearch 而不是 MySQL 的 `like`？ES 和 MySQL 的数据一致性怎么保证？浏览量的统计为什么用 Redis 计数？

**问题**：请结合项目说明引入 ES 的动机、ES 与 MySQL 双写的同步策略，以及浏览量计数用 Redis INCR + 定时回刷的设计（而不是每次浏览直接 UPDATE 数据库）的原因。

> **考察点**：考察候选人对"引入新技术是为了解决什么具体问题"的思考，以及缓存计数与最终一致性这类常见的工程优化手段。

**参考答案**：

- **为什么用 ES 而非 `like`**：
  - `LIKE '%关键词%'` 无法走索引（前导模糊导致索引失效），数据量大时全表扫描极慢；
  - ES 基于**倒排索引**，对文本做分词后建立"词 → 文档"的映射，全文检索、多字段匹配、高亮、相关性排序都是它的强项；
  - 职位搜索需要按标题、描述、技能、城市等多维组合检索，ES 天然适合。
- **ES 与 MySQL 一致性**：**以 MySQL 为主库**，ES 是衍生索引。职位发布/审核通过/编辑/下架时，同步写 ES（`indexJob`/`deleteJob`）；**同步失败只记日志不影响主流程**，因为 ES 索引可随时全量重建（项目里就有 `syncAllJobsToEs` 全量同步兜底）。这是"最终一致"的典型做法。
- **浏览量为什么用 Redis 计数**：
  - 如果每次浏览详情都 `UPDATE view_count = view_count + 1`，会对 MySQL 产生大量写压力，且是热点行竞争；
  - 用 Redis `INCR` 原子自增，扛住高频浏览，再由定时任务（`ViewCountFlushTask`）批量回刷 MySQL，Redis 不可用时降级直接改库。这是典型的"写缓存 + 异步回刷"削峰手段。

- **个人贡献**：除了核心模块编码，还有技术选型、架构拆分（微服务的服务边界划分）、公共组件封装、新人答疑等。要能讲出一两个有细节的真实案例，比泛泛而谈"我很会协作"有说服力得多。

## 七、工程能力与 AI 工具应用（1 题）

### Q23. 你熟练使用 Codex、WorkBuddy 这类 Agent 工具，还了解 Function Calling 机制，能举一个你实际用它提效的例子吗？

**问题**：请说明你在日常开发中如何通过 Prompt 工程让 AI 帮你写代码、排查问题，Function Calling 在你理解里是如何让模型调用"查询数据库、检索知识库、调用内部接口"这些能力的？你如何看待 AI 工具在真实工程里的边界和风险？

> **考察点**：AI 原生开发者的工程素养，也是简历里最差异化的一项能力。

**参考答案**：

- **Prompt 工程提效**：把需求描述清楚（给足上下文、约束、期望输出格式），让 AI 生成代码骨架、单元测试、正则、SQL 等；排查问题时把报错堆栈、相关代码片段一起喂给 AI，加速定位。
- **Function Calling 理解**：模型本身不能执行操作，Function Calling 是让模型在需要时"请求调用"一个外部函数——模型输出一个结构化的"函数名 + 参数"的调用请求，由程序实际去执行（查数据库、检索知识库、调内部接口），再把执行结果返回给模型，让模型基于真实数据继续回答。这样模型就从"纯聊天"变成了"能操作真实系统"的 Agent。
- **边界与风险**：AI 生成的代码要**人工审查**（正确性、安全性、性能），不能盲信；涉及敏感数据、生产环境操作时要谨慎；AI 是效率放大器，不是替代品，最终责任在人。
